@import controllers.{FilmFormat, FilmSchedule, CardFormat, FilmHref, ShowingsMarkup} @(film: FilmSchedule)(implicit city: models.City) @* One film's showings, grouped by date → cinema → time slots. Used by `_filmCards` (the listing) and `_filmDetailContent` (the per-film page). The cinema sub-header names each cinema (and links to its page for the film when available); the format tokens the whole card shares are stripped from each slot's badge. The label is always shown on the listing — even when the cinema filter is narrowed to one cinema. A token every slot of the film carries is dropped whatever it names — a screen format or a language version alike — because it separates no slot from any other. Two cinemas that disagree make the film mixed even though neither cinema is, and then every pill keeps its version. See `FilmFormat`. Both outbound shapes here — the cinema's page for the film, and each slot's booking deep-link — carry `rel="nofollow"` and open in a new tab. A city listing renders thousands of them (one per showtime); they're plumbing, not endorsements. `noopener` is left to the browser, which applies it to every `target="_blank"` link on its own. THE TREE ITSELF IS `ShowingsMarkup.days`, NOT TWIRL. Per day, per cinema and per showtime, a template allocated a fragment object for every static run of markup and an escaped `Html` for every value — 72 MB a render on New York — where one pre-sized builder per film costs a fraction. What the markup leaves out for the same reason (booking-URL prefixes, `data-cinema`, repeated cinema links) `ShowingsMarkup` lists, and `_showingsHydrate` puts back in the browser before anything reads it. EVERY cinema is rendered, on both hosts. What narrows the list is the visitor's own Filtry selection, applied client-side: the listing does it in `_repertoireView`'s `applyFilters`, the film page in the one `film.scala.html` defines.
