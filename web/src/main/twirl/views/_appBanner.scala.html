@()(implicit city: models.City, messages: play.api.i18n.Messages) @* App-promo top banner — its markup AND the whole show/hide decision, which runs in the inline script right after the markup: synchronously, while the parser is still above the navbar, so the banner is up (and the page pushed down by it) before the first paint. It used to be revealed by the deferred `shared.js`, one frame after its checks — the navbar painted at the top and then dropped by the banner's height, a layout shift every visitor saw. Two independent localStorage gates decide it. The interval cap is DEVICE-AWARE: a touch/coarse-pointer visitor (a phone, our best market) sees it once per calendar day, a fine-pointer one (desktop) once every 10 days — desktop traffic is far less likely to install a phone app (Paweł's call, 2026-09-14). It keys off the CITY's calendar day (`data-zone`) read off the VISITOR's clock, and counts days since it was last shown. Not the page's render day: a body the browser serves from its own cache (a 304, the back/forward cache) keeps its render's day, and the cap compares against localStorage stamps a fresher page wrote. The ✕ sets a rolling 24h snooze from the click instant, always shorter than either interval. `?forceAppBanner=1` bypasses both, and every visit logs its gate state to the console (`[app-banner] {…}`) so "I don't see it" can be diagnosed from the visitor's own console. The one asynchronous check, Android Chrome's `getInstalledRelatedApps()` ("is the Play app already installed?", no iOS/Safari equivalent), can therefore only HIDE a banner that is already up. That hide is a shift too, but only for an Android Chrome visitor who has the app installed, and it resolves within the first moments of the load — deferring the banner for every Android visitor instead would bring the shift back for the common case. Starts with neither badge shown (`style="display:none"`) so a JS-disabled visitor never sees a banner with nothing it can act on. Store URLs come from `models.ClientSupport` — the SAME record the mobile apps' own update-gate reads (`GET /api/client-support`). Brand name and copy are per-country: `city.country.brandName` is "Kinowo" only in Poland, "Showtimes" everywhere else. *@
